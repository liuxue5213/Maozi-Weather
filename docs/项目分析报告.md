# 毛仔天气 项目分析报告

> 分析范围：后端数据拉取实现、Web 管理端（web-admin）、Android 端（apk）
> 结论先行：**后端数据层已可用但存在架构分叉与若干正确性/健壮性问题；Web 管理端功能基本可用但偏"管理后台"；Android 端目前只是 UI 骨架，核心功能（登录、拉数据、缓存、城市管理）均未真正实现。**

---

## 0. 架构总览

```
前端                      后端 FastAPI                  数据源
─────────────            ───────────────────            ───────────────
web-admin(Vue3)  ──JWT──▶ /api/weather/*  ──▶ multi_source_weather
                                │                ├─ Open-Meteo（主，免费）
                                │                ├─ QWeather（增强，需Key）
                                │                └─ CMA（仅 WeatherService 引用，未接入）
/android(Kotlin) ──JWT──▶ /api/weather/*  ──▶ multi_source_weather
                   （注意：apk 调用时缺 latitude/longitude）
/api/public/weather ──────────▶ 直接代理 Open-Meteo（无鉴权、无缓存、无限流）
```

**关键事实（与 README 矛盾）**
- README 声称"对接中国气象数据网（CIMISS/天擎）官方 API"，但路由实际只调用 `multi_source_weather`，其主源是 **Open-Meteo（免费免 Key）**。`cma_client` 与 `WeatherService` 是**死代码**（仅被自身和 scheduler 的 TODO 注释引用，没有任何路由使用）。
- `config.WEATHER_PRIMARY_SOURCE` / `WEATHER_FALLBACK_ENABLED` / `CMA_*` 等大量配置**从未被读取**（Open-Meteo 路径完全忽略这些开关）。
- 实况/预报/空气质量**只进 Redis 缓存，不落 MySQL**；`WeatherRealtime`、`WeatherForecast` 两张表已定义但**从未被写入**（纯死 schema）。

## 1. 后端天气数据拉取实现（重点）

### 1.1 多源服务 `multi_source_weather.py` ✅ 主体可用
- Open-Meteo 主源 + QWeather 备源切换逻辑清晰，`normalize_*` 把不同源统一为标准字段，思路正确。
- 实时：`get_realtime` 调 Open-Meteo `get_forecast(current=...)` 仅取 `current`，✅ 可行。
- 历史：`get_historical` 走 Open-Meteo archive，✅ 可行。

### 1.2 问题清单（按严重度）

🔴 **【严重·正确性】AQI 数值体系错位**
`open_meteo_client.normalize_air_quality` 与 `public.py` 把 Open-Meteo 的 **`european_aqi`（欧标）** 直接当成 `aqi` 字段返回，并套用"优/良/轻度污染…"中文等级。
- 欧标 AQI 与**国标 AQI（GB3095，0-50 优、51-100 良…）刻度完全不同**。前端 `Weather.vue` 的 `aqiColor` 也是按国标阈值上色。
- 后果：显示的数值和颜色含义都对不上（例如欧标 42="优"对，但欧标 120 在国标里早已"中度"，这里仍显示"良"）。
- 修复：`aqi` 字段应明确命名为 `european_aqi`，或调用 `air_quality_service.calculate_aqi` 用污染物浓度换算国标 AQI（后端的 `calculate_aqi` 是正确的国标算法，但前端走的 `/weather/air_quality` 没用它）。

🟠 **【高·健壮性】预警/生活指数/日出日落 缓存 key 不含参数**
`multi_source_weather.get_warning` 等缓存 key 仅含 `city_id`，但 QWeather 预警依赖 `location_id`。不同 `location_id` 会读到同一份缓存，且 `get_forecast` 的 `days` 参数也未进入缓存 key（7 天请求可能命中 16 天缓存）。

🟠 **【高·调度器失效】缓存预热定时任务全是空壳**
`scheduler.py` 中 `refresh_realtime_cache / refresh_forecast_cache / refresh_warning_cache` 全部是 `pass` + `TODO`。即 APScheduler 每 10 分钟/1 小时触发，但**什么都不做**，Redis 缓存只能被动命中（首次请求才回填）。所谓"定时拉取关注城市"并未实现。

🟡 **【中·并发】历史同步任务的重复执行风险**
`process_history_tasks` 每分钟选 1 条 `pending/failed` 任务，用 `asyncio.create_task(execute_sync_task(...))` 异步跑，**但创建任务前没有先把状态置为 running**：
- 若任务执行 >1 分钟，下一分钟调度器会再次选中同一任务 → **并发重复拉取**。
- `failed` 任务被 `execute_sync_task` 重新置回 `failed` 后，下一分钟又会被选中 → **无退避的无限重试风暴**。
- 应在选中后立即 `UPDATE status='running'` 并提交（原子），再 `create_task`；并对 `failed` 加重试次数上限/退避。

🟡 **【中·数据丢失】历史同步丢弃字段**
`history_sync.execute_sync_task` 请求了 `weather_code`、`temperature_2m_min`，但只写入 `temperature`(取 max)、`wind_speed`、`precipitation`；`min` 温度与天气现象被丢弃。`HistoryObservation` 表的 `pressure/humidity/wind_direction` 列永远为 NULL（从未写入）。

🟡 **【中·设计】`/api/public/weather` 与鉴权体系冲突**
`public.py` 的 `/weather` 是**完全公开、无 JWT、无缓存、无限流**的 Open-Meteo 代理，把 `multi_source_weather` 里已有的逻辑又重写了一遍（大量重复代码）。README 明确"所有业务接口需 JWT 鉴权"，此处直接违反，且是上游调用滥用的入口。

🟡 **【中·安全】CORS 配置有坑**
`main.py`：`allow_origins=["*"] if APP_DEBUG else []` + `allow_credentials=True`。
- DEBUG=True 时 `*` 与 credentials 共存，部分浏览器/规范下无效；
- **DEBUG=False 时 origins 为空数组 → 所有跨域请求被拒，Web 端直接连不上**。生产环境必须显式列出前端域名。

🟢 **【低·质量】CMA 限流器非严格令牌桶**
`CMARateLimiter.acquire` 取不到令牌时 sleep 一次后直接放行（不二次校验），高并发下可能瞬时超出 `CMA_QPS_LIMIT`。（但因 CMA 当前未接入，暂不影响运行。）

🟢 **【低·质量】散落的 `import json`**
多个 service 在函数内重复 `import json`，应提到模块顶部。

## 2. Web 管理端（web-admin / Vue3）

### 功能现状
- 已实现的页面：登录、控制台(Dashboard)、城市站点管理、实时天气(Weather)、历史同步、历史查询、数据分析、系统配置、监控日志。
- 实时天气页 `Weather.vue`：选城市 → 并行拉取 实况/预报/预警/空气/生活指数/日出日落，展示完整，**逻辑基本正确**。

### 问题
🔴 **【严重·契约不一致】前端把"中国气象局"当数据来源，但实际是 Open-Meteo**
`Weather.vue` 底部写死"数据来源：中国气象局"，`dataSource` 显示的是后端返回的 `data_source`（Open-Meteo/QWeather）。对用户/审计是**误导性标识**，且与 README 一致地"虚构"了官方数据源。

🟠 **【高·健壮性】城市缺经纬度直接中断**
`Weather.vue` 若 `city.latitude/longitude` 为空就 `return` 不再请求。但后端 `/weather/realtime` 等**强制要求 lat/lon**，所以城市库若没维护经纬度，整个天气页不可用。后端应允许"只传 city_id 由后端自己查经纬度"。

🟡 **【中】`getRealtime` 的 `BaseModel` 与返回结构**
`router` 用 `response_model=WeatherRealtimeOut`，但 `multi_source_weather.get_realtime` 返回 dict（字段含 `weather_desc` 等），需确认 schema 字段对齐，否则 422/500。建议补一个端到端冒烟测试。

🟢 **【低】`console.log` 调试残留**：`loadCities` 里 `console.log('加载城市数量:...')`，生产应移除。

🟢 **【低】`index.html` 与 `vite.config.js`**：`public/weather.html` 疑似未使用的静态页，可清理。

## 3. Android 端（apk / Kotlin + Compose）

### 功能现状 ⚠️ 基本是 UI 骨架，核心功能未实现
| 模块 | 状态 |
|------|------|
| 登录 LoginScreen | ❌ 按钮直接 `onLoginSuccess()`，**从不调用 `/api/auth/login`**，等于无登录 |
| 首页 HomeScreen | ❌ 城市列表 `emptyList()`，卡片写死"北京 25°C 晴"（`TODO: 从 ViewModel 获取`） |
| 天气详情 WeatherDetailScreen | ❌ 全部写死静态数据（25°C/优/05:42 日出…） |
| 城市管理 / 历史 / 设置 | ❌ 显示"待实现" |
| RetrofitClient / ApiService | ⚠️ 已定义，`WeatherApplication.onCreate` 调了 `init()`，但**没有任何 Screen 真正调用** |
| Room 缓存 CachedWeather | ⚠️ 已定义，`WeatherApplication.database` 已实例化，但**没有任何地方读写**（离线缓存未接入） |
| TokenManager（DataStore） | ⚠️ 仅在 `RetrofitClient` 拦截器里用，登录不存 token，等于鉴权链路断开 |

### 问题（按严重度）

🔴 **【严重·契约】ApiService 调用缺必填参数，必然 422**
```kotlin
@GET("/api/weather/realtime/{cityId}")
suspend fun getRealtime(@Path("cityId") cityId: Int): WeatherRealtime  // 没传 latitude/longitude
```
后端 `get_realtime` 要求 `latitude: float = Query(...)`、`longitude: float = Query(...)`（必填）。**一旦接上真实接口，实况/预报/空气质量三个接口全部 422 失败**。必须补 `@Query("latitude")/@Query("longitude")`，并从城市数据取经纬度。

🔴 **【严重·功能缺失】没有任何 ViewModel / 数据层调用**
所有 `@Composable` 都是纯静态展示，连 `RetrofitClient.apiService` 都没被调用。等于 App 现在**打不开真实数据**。

🟠 **【高·安全/逻辑】登录绕过鉴权**
`LoginScreen` 不校验账号密码、不请求后端、不保存 token。即使后续接 ApiService，若用户未登录，拦截器不加 `Authorization`，后端 401。

🟠 **【高·资源泄漏】HttpLoggingInterceptor 打 BODY 级别**
`RetrofitClient` 用 `Level.BODY`，会明文打印请求/响应体（含 token）。生产必须降级为 `BASIC`/`NONE`，且 `release` 构建应关闭。

🟡 **【中·离线缓存未接通】**
Room `CachedWeather` 表与 DAO 已实现，但无 `insert`/`query` 调用，无网络失败回退逻辑。"离线看天气"未实现。

🟡 **【中·缺少桌面小组件/预警推送】**
README 承诺的"Android 桌面小组件 + 预警推送"：代码里只有 `WeatherApplication.createNotificationChannel()` 建了渠道，**没有任何推送逻辑、也没有 WorkManager 定时拉取**（虽然依赖里加了 `work-runtime-ktx`，但没使用）。

🟢 **【低】硬编码 BASE_URL `http://10.0.2.2:60245`**
仅适配模拟器，真机/其他环境需可配置（BuildConfig / 远程配置）。

## 4. 后续"拉取天气数据"实现建议（落地路线）

1. **统一数据源真相**
   - 删除或真正接入 `WeatherService`/`cma_client`（要么去掉死代码，要么把 CMA 作为第三备源接进 `multi_source_weather`）。
   - 让 `WEATHER_PRIMARY_SOURCE` 真正生效，避免"配置有、代码不读"。

2. **修复 AQI 体系**
   - `aqi` 明确为欧标或换算国标；前端颜色阈值与后端等级保持一致。建议后端 `/weather/air_quality` 直接复用正确的 `calculate_aqi`（国标）。

3. **让 scheduler 真正干活**
   - `refresh_*_cache` 从"关注城市表"取列表，逐城调 `multi_source_weather` 并写 Redis（避免首请求冷启动慢）。
   - 历史任务：选中即置 `running` 再 `create_task`；`failed` 加重试上限 + 指数退避。

4. **缓存 key 含参数**
   - 预警 key 含 `location_id`；预报 key 含 `days`。

5. **对外契约对齐**
   - 后端：`latitude/longitude` 改为可选，缺失时由后端用城市表经纬度补全（前端已依赖 city 数据）。
   - Android：`ApiService` 全量补 `latitude/longitude`；新增 `ViewModel` 层真正调用接口 + 写 Room 缓存 + 失败回退。

6. **安全收口**
   - CORS 显式白名单；`public.py` 要么加鉴权+缓存+限流，要么下掉让前端统一走 `/api/weather/*`；OkHttp 日志降级；登录真正校验并保存 token。

7. **Android 优先级（让 apk 真正能用）**
   - ① 登录接入 `ApiService.login` + `TokenManager.saveToken`；
   - ② 关注城市用 `getMyCities` + `CityManageScreen` 实现增删；
   - ③ `HomeScreen`/`WeatherDetailScreen` 接 ViewModel，用 `getRealtime/getForecast/...` 替换写死数据；
   - ④ 网络失败读 `CachedWeather` 离线展示；
   - ⑤ WorkManager 定时拉取 + 预警推送（读 `weather_warning` 表/接口）。
